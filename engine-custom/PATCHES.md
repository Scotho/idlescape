## The production floor (`src/idlescape/config.ts`)

`loadIdlescapeConfig` forces `requireOwner` true whenever `node.production` is true, and since
the deploy fix for audit C07 it also **refuses to start** a production world whose owner secret
is empty, from either source (the environment or `data/config/idlescape.json`).

Why a throw and not a default: with `requireOwner` forced on, an empty secret is not "owner
binding off". `PlayerLoading.load` verifies every login's assertion against `''`, fails, and
`World.onLoginMessage` answers login response 13 - so the world comes up, reports healthy, and
refuses every player one at a time. That is invisible to a deployment; a process that will not
start is not. The message names `OWNER_ASSERTION_SECRET`, which is what
`deploy/lightsail/provision.ps1` writes into the box's `server.env` and
`deploy/docker/docker-compose.yml` env_files into both containers.

Dev is untouched: `requireOwner` is false there, an empty secret means no owner binding, and
that is a working local world. `src/idlescape/config.test.ts` covers all three cases (throws
from either source in production, loads from either source in production, and a secret-free dev
world still loads).

### `src/engine/entity/PlayerLoading.ts` - verify the assertion and stamp the owner key (hunk 1 of 3)

Anchor: `static load(name, sav, client)`, immediately after
`const player = client ? new NetworkPlayer(...) : new Player(...)` and before
`player.lastConnected = World.currentTick;`. Plus three imports added to the existing block:
`#/idlescape/config.js`, `#/idlescape/owner.js`, `#/idlescape/ownerAssertion.js`.

Why here and not in `World.readLogin`: `load` is the first place that sees both the decrypted,
`toSafeName`d username *and* the `ClientSocket` the header was captured on, and it is already
wrapped in a `try/catch` in `World.onLoginMessage` that answers a throw with login response
**13** and a `player_force_logout` post that the single-world login thread ignores
(`LoginThread.ts` only acts on that message when `Environment.login.enabled`). That gets a
correct rejection out of a 165-line replacement instead of a 2,375-line one. The `World.ts`
anchor in `manifest.json` pins that `try/catch`.

The comparison is the whole security property. The login block is RSA-encrypted end to end, so
the relay never learns which character the socket is logging in as; only the engine does, and
only here. `verifyOwnerHeader` is given `safeName`, i.e. the engine's own
`fromBase37(toBase37(name))`. Checked in the clone (`src/util/JString.ts`): `toSafeName` is
exactly that pair, `toBase37` folds `A-Z` onto the same values as `a-z` (`c + 1 - 0x41` and
`c + 1 - 0x61`) and drops every other character, and `fromBase37` emits from an all-lowercase
lookup table. So `safeName` is always lowercase `[a-z0-9_]{1,12}`, which is exactly the shape
the front server signs its normalised `gameName` in, and a player who types `AlIcE` matches the
entry signed for `alice`. `src/idlescape/ownerAssertion.test.ts` pins that.

With no valid entry the login still proceeds **un-stamped** unless `idlescapeConfig.requireOwner`
is set, so the dev world (no secret, `requireOwner=false`) is unaffected; production forces
`requireOwner` on in `config.ts`. Anything downstream that needs the owner asks
`hasOwnerKey`/`getOwnerKey` rather than assuming one is present.

The throw is guarded with `client &&` (Task 9). `PlayerLoading.load` is also called with a
`null` socket by the standalone login server - once per autosave merge
(`LoginServer.wouldResetSaveFile`) and once per hiscores update - and those calls decode a
`.sav` off disk with no socket, so no header, so no assertion. Without the guard a production
world would start refusing its own autosaves. A `null` client can never carry an assertion in
the first place, so it can never be stamped either: those loads are un-stamped by construction
and read inv 95 straight out of the `.sav`, which is exactly what a save-file merge needs.

### `src/engine/entity/PlayerLoading.ts` - the .sav bank is handed to the owner store (hunks 2, 3, 4)

Three more hunks, all conditional on the `ownerKey` hunk 1 computed
(`const ownerKey = owner ? owner.uid : null;`, added right after the assertion block), plus
`let pendingBank: BankSlotDto[] = [];` beside the `const player = ...` line and three imports:
`#/idlescape/install.js` (`ownerBanks`), `#/idlescape/tabVarps.js` (`writeTabVarps`) and
`#/idlescape/types.js` (`BANK_INV_NAME`, `BankSlotDto`).

**Hunk 2** - anchor: the inventory-loading loop, inside
`if (invType.scope === InvType.SCOPE_PERM)`. An owner-stamped player's inv 95 is decoded but
NOT written: the slots go into `pendingBank` and the loop `continue`s. Writing them would push
one character's `.sav` bank into the shared container on every single login, so two characters
of one account would overwrite each other's bank at each login. The decoded slots are held for
the one-time migration in hunk 3 instead.

**Hunk 3** - anchor: the tail of `load`, the two lines
`player.combatLevel = player.getCombatLevel(); return player;`. `banks.migrate(ownerKey,
safeName, pendingBank)` folds the character's legacy bank in once ever, then
`writeTabVarps(player, banks.tabs(ownerKey))` seeds the nine in-game tab varps from the store.
Nothing here retires, blanks or rewrites the `.sav` bank on any outcome: the `.sav` stays the
source of truth until a merge actually lands.

**A REFUSAL is not "already merged", and the difference is the character's items.** `migrate`
answers `'merged' | 'already' | 'refused'` (it used to answer a boolean, which folded the last
two together). On `'refused'` - the merge would overflow the shared container, it names an obj
this pack does not have, or the owner has writes suspended - those items exist ONLY in this
character's `.sav`, and `Player.save()` serialises `this.invs`, which hunk 2 deliberately left
without a bank. Left alone, the next autosave or logout would rewrite the save with no bank
section at all and the items would be **gone**; the refusal is reachable in normal play, because
a second or third character's bank need not fit alongside the first in one 240-slot container.
So a refusal writes `pendingBank` back into the character's OWN container, through
`ownInventory(player, ...)` (`src/idlescape/install.ts`), which is upstream's `getInventory`
saved by Patch 1 - the PATCHED one would answer a stamped player with the shared container and
swallow the items a second time. `save()` then re-emits the bank verbatim and the next login
retries the merge. That container is never read in game: inv 95 still resolves to the store.
Pinned by `src/idlescape/shared.test.ts` (a refused login's save still carries inv 95 with the
same slots; a merged one does not).

**Hunk 4** - anchor: the `if (sav.data.length < 2)` new-character branch, just above its
`return player;`. The same `writeTabVarps` seeding, because that branch returns before hunk 3.
This is an addition to the Task 9 brief, and it is load-bearing rather than cosmetic: the
post-cycle hook mirrors each online character's tab varps INTO the store every tick, so a
brand-new character of an existing owner that started with nine zeroed varps would push an
empty tab layout over the one every other character of that account shares, on its first tick.

### `src/server/login/LoginThread.ts` - staff level is an allow-list, not a build flag

Two hunks, both deleting an upstream `staffmodlevel = 4` that fires whenever
`node.production` is false: one in the multiworld branch just after `client.playerLogin(...)`,
one in the single-world branch just above `const profile = Environment.node.profile;`. Both
now call `staffLevelFor(username, ...)`. The login worker never sees the socket, so the owner
assertion cannot reach it; the allow-list in `data/config/idlescape.json` is the only source
of a non-zero level, plus `IDLESCAPE_DEV_STAFF` which `config.ts` forces to 0 in production.

Ruling: the assertion does **not** carry a staff level in v1. The login worker runs in a
worker thread and never sees the socket, so the only value it can source is the username;
staff level therefore comes from an explicit allow-list in `data/config/idlescape.json`
(`{"staff": {"someadmin": 2}}`), defaulting to **0** for everyone. `IDLESCAPE_DEV_STAFF` is
the escape hatch for local play and is forced to 0 whenever `node.production` is true
(`config.ts`, Task 2). Upstream's blanket `staffmodlevel = 4` when `!production` is deleted
from both branches. Allow-list keys must be written in the engine's `toSafeName`
form: `config.ts` lower-cases them as it reads the file and `staffLevelFor` lower-cases the
username it is given, but that username has ALREADY been through `toSafeName` in
`World.readLogin` (the login worker is posted `username: safeName`), so it is lowercase with
spaces as underscores. An entry for `someadmin` therefore matches a player who typed
`SomeAdmin`, while an entry for `Some Name` matches nobody at all - it must be written
`some_name`.

Adding the two imports (`#/idlescape/config.js`, `#/idlescape/staff.js`) is the third change in
the file. Nothing else in it changes; both modules are leaf modules with no engine imports of
their own beyond `Environment`, which the login worker already loads.

Two properties of hunk 1 worth stating, because they are not obvious from the diff:

- It **overwrites** `response.staffmodlevel` rather than defaulting it, so a level supplied by
  a multiworld login server is demoted to the allow-list value. That is the fail-safe
  direction: the allow-list in `data/config/idlescape.json` is the only authority on staff
  level in this deployment, and an upstream login server we do not control cannot promote
  anyone by answering with a 4.
- The allow-list is read **once at boot**, when `config.ts` evaluates `idlescapeConfig`, and
  the login worker holds its own copy of that module. Editing `data/config/idlescape.json`
  therefore takes effect at the next engine restart, not at the next login.

## Runtime patches (installed by `src/idlescape/install.ts`)

(One section per prototype/method patch, added by the task that introduces it.)

### Patch 1: `Player.prototype.getInventory` routes inv 95 to the owner store

Anchor: `getInventory(inv: number): Inventory | null {` in `src/engine/entity/Player.ts`, the
method that branches on `InvType.SCOPE_SHARED` and otherwise fills `this.invs` from
`Inventory.fromType(inv)`. The overlay saves that function and installs a replacement that adds
exactly one branch in front of it: an owner-stamped player asking for the bank inv gets
`ownerBanks().get(ownerKey)`; everything else, and every un-stamped player, falls through to
the original by `.call(this, inv)`.

**Ruling 1: it is patched at runtime, not replaced.** Upstream's method is 24 lines inside a
2,304-line file. A whole-file replacement would carry 2,280 lines of upstream code we do not
change and would rot invisibly on a revision bump. The patch is recorded in `manifest.json`'s
`anchors` instead, so `-Check` fails when `Player.ts` moves at all. `Inventory.ts` is anchored
for the same reason: the store and `applyOps` depend on its `set()`/`markDirty()`/
`resetTracking()` semantics.

**Ruling 2: `Player.save()` needs no patch at all.** It iterates `this.invs`
(`Player.ts:229-231`); an owner-stamped player never has 95 in that map, because the patch
returns the store's container **without inserting it**, which is the whole reason it is written
that way rather than as a `this.invs.set(95, ...)`. Pinned by
`src/idlescape/install.test.ts`, which decodes the `.sav` a stamped player produces and asserts
inv 95 is absent from it while inv 93 is present.

The one exception is deliberate and is the other half of that property: a character whose `.sav`
bank could NOT be migrated gets those slots put back into `this.invs` at login (PlayerLoading
hunk 3), so `save()` re-emits its own bank rather than dropping it. The shared container is
still never in `this.invs`, so what is written there is the character's own legacy bank, exactly
as it was read.

The assignment needs one local type annotation, `function (this: Player, inv: number)`, and no
cast: the replacement is type-checked against the method's own signature.

### Patch 2: `World.cycle` is wrapped so the owner containers are swept after client output

Anchor: `for (const inv of player.invs.values())` in `World.processCleanup`
(`src/engine/World.ts`), the reset the owner container is deliberately outside of, and the
`setTimeout(this.cycle.bind(this), ...)` at the end of `cycle()`.

**Ruling 3: wrapped, not replaced.** `cycle()` reschedules itself with
`setTimeout(this.cycle.bind(this), ...)`, so an own-property override on the `World` singleton
is picked up from the very next tick, provided `install.ts` runs before `World.start()` - which
is why the replaced `src/app.ts` imports it first. The wrapper calls the original, then
`afterCycle()` inside a `try/catch`: a throw out of the hook would land in `cycle()`'s own
catch, whose recovery is to remove every player from the world.

**Ruling 4: cross-character updates are live, not stale.** The spec (section 7) accepts one
character's bank interface going stale while another banks. It does not have to.
`processCleanup` resets tracking only for `player.invs`, and the owner container is deliberately
outside those maps, so the overlay owns the reset - and it does it in the post-cycle hook,
*after* `processClientsOut` has written every player's inv diff. Both online characters
therefore receive the same `UpdateInvPartial` in the same tick. The spec's accepted staleness is
recorded as no longer applicable; SP8b can rely on live updates.

**Only a character that MOVED its own tabs mirrors them in.** The pass compares each online
character's varps against the layout the overlay last WROTE to that character
(`changedTabVarps`, a `WeakMap` in `src/idlescape/tabVarps.ts` that `writeTabVarps` keeps up to
date) and calls `setTabs` only on a difference. Mirroring every character unconditionally is
last-writer-wins across the characters of one account: with two of them online, whichever the
loop reached last decided the account's layout, so a character that did nothing reverted one
that had just rearranged its tabs, and the next tick pushed that reversion back out to both.
Everything that writes these varps writes the STORE's layout (the login seed in PlayerLoading
hunks 3 and 4, and the push-out below), so "differs from what we wrote" is exactly "the player
moved it". A character nothing has been written to yet has no snapshot and mirrors in on its
first tick, which is what keeps a newly stamped character from being frozen out. Latent in SP8 -
nothing writes `banktab_size_*` until SP8b - but SP8b must not be built on it.

**The push-out loop guards each owner separately.** `bumpDirty()` has already consumed the dirt
and bumped every version by the time that loop runs, so there is nothing left to retry from: a
throw escaping the body (a `writeTabVarps` that fails for one character) would cost every owner
AFTER it its change hook, permanently, leaving the front server's `versions` map stale with
nothing to correct it. Each owner's post-and-push is therefore wrapped in its own `try/catch`
and logged through `logCycleFailure`. Persistence was never at risk here - `dirtyFile` is
already set - only the notification.

`afterCycle()` also flushes dirty owners to disk every 100 ticks (1 minute) - the periodic
cadence only; the two paths that LEAVE the process are Patch 3's - and evicts unused
containers every 1,500 (15 minutes, the autosave rate), and posts the change hook for every
owner `bumpDirty()` reports. It walks the online players exactly ONCE per tick: that pass
mirrors the tab varps in and builds a `Map<ownerKey, Player[]>` which both the sweep (pushing
the tab layout back out) and the eviction predicate reuse, so the cost is linear in players
rather than players times dirty owners. `notifyBankChanged` is fire and forget - `void
fetch(...)` with a 2 s `AbortSignal.timeout` and a `.catch` that logs - because awaiting it
would put an HTTP round trip inside the tick; it is a no-op when `idlescapeConfig.hookUrl` is
null (the dev world) or when `idlescapeConfig.managementSecret` is empty (an unsigned post the
front server can only refuse).

**It inspects the RESPONSE, not just the transport.** A 401, a 404 or a 5xx RESOLVES the fetch
promise, so a bare `.catch` cannot see it - which is exactly the blindness that let Task 10's
wrong-secret bug live: every post was refused and nothing said so. `logHookFailure(!res.ok, ...)`
logs the status and the owner key. Nothing it can log is sensitive: the two log lines name the
owner key plus either an HTTP status or a transport error, never the request body (no item data)
and never the header (no secret).

Both that log and the post-cycle wrapper's own error log go through `failureLog()`, the
"until it recovers" cousin of the store's `warnOnce`: one line per transition INTO failure,
cleared by the next success, with a separate throttle each so a change hook that is down cannot
silence a sweep that is broken.

What that guarantees is bounded, not silent: the sweep throttle is a true one-per-outage,
because there is one sweep per tick, but the HOOK throttle is global across owners rather than
per owner. Under a total outage it is also one line per outage; under a PARTIAL failure (one
owner's post 404ing while other owners' posts succeed) the successes re-arm it between the
failures, so the ceiling is one line per changed owner per tick rather than one per tick. That
is still bounded by the number of owners who changed, which is what a per-owner throttle would
have cost in memory anyway, and a partial failure is a case worth being noisy about.

The pass over the online players is also where an **externally applied tab layout travels
outwards**. `afterCycle` reads `banks.externallyApplied()` (which does not clear the flag;
`bumpDirty` remains its only consumer) BEFORE the sweep, and for an owner in that set it calls
`writeTabVarps(player, banks.tabs(ownerKey))` instead of mirroring the player's varps in. Without
that, an external `setTabs`/`moveToTab`/`sort` landing between ticks would be overwritten one
tick later by the online character's still-stale varps, and `bumpDirty`'s flag branch would then
clear the `tabsChanged` that overwrite set: no bump, no hook, no push-back, and the store
silently serving the stale in-game layout at the version the web client was just handed. Before
the one-shot flag existed the second bump made that self-correct; it does not any more, so the
direction is chosen explicitly.

**The ruling on a same-tick collision: the web caller wins.** When an in-game tab drag and an
external apply land in the SAME tick, the drag is discarded and the applied layout is written
over the player's varps. The web caller holds a version number for its change and expects it to
stick; the player holds nothing, sees the tabs snap back within a tick, and can simply drag
again, which the next tick mirrors in as usual. Losing the web caller's change instead would
strand a version that no longer describes the bank. Only the tab LAYOUT is resolved this way -
the item change behind an in-game action still lands in the shared container and is folded into
the apply's version (see the store section).

**Push-out is armed by ANY apply, not only one that touched the tabs.** The flag lives on the
entry, not on the tab array, so an item-only `delta` from the web also puts the owner in
push-out mode for the following tick. **Cadence matters for SP8b**: a client that applies on
most ticks - a drag-sort session sending one op per drag - holds the owner in push-out mode
continuously, and for as long as it does, in-game tab rearrangement by that account's characters
cannot land at all. Batch the ops, or accept that in-game tab drags are suppressed while a web
bank window is actively writing.

One ordering consequence of doing the push in the pre-sweep pass: `writeTabVarps` calls
`player.setVar`, so a throw out of it now happens BEFORE `bumpDirty`, the change hooks, `flush`
and `evict`, and would skip all of them for every owner that tick. The wrapper's `try/catch`
still keeps the world alive (and now logs once per outage rather than once per tick), and the
next tick retries from the same state, because nothing the skipped sweep would have consumed was
cleared. `OwnerBankStore.apply` bumps the version
synchronously on the external write path, so the hook a management write needs is Task 10's to
send; `afterCycle` covers in-game mutations only, and a store refusal
(`{ ok: false, reason: 'unavailable' }`) never reaches it because a refused apply changes
nothing for `bumpDirty` to see.

**Ruling 5: tab varps.** Nine `scope=perm` varps `banktab_size_1..9`
(`content-custom/scripts/interface_bank/configs/banktab.varp`) mirror the store's tab sizes.
They are seeded from the store at login (`PlayerLoading` hunks 3 and 4) and read back once per
tick for owner-stamped players; a difference updates the store, which the same tick's
`bumpDirty` turns into a version bump and a change-hook post. `src/idlescape/tabVarps.ts`
memoises the nine ids, but never before `VarPlayerType` is loaded, so an ordering accident
cannot freeze them at -1 for the life of the process.

**An interior zero tab size collapses and the tabs renumber.** `OwnerBankStore.setTabs` (and
the file reader) keep only the sizes that are positive integers, so varps reading `[3, 0, 2]`
are stored as `[3, 2]`: tab 3 becomes tab 2. Because the same tick's `bumpDirty` reports the
owner, `afterCycle` writes the store's layout straight back out, so the player's own varps are
renumbered to `[3, 2, 0, ...]` too - the collapse is not silently one-sided. This is the
trailing-zero trim of `tabVarps.ts` generalised: a zero size is never an empty tab held open in
the middle of the layout, which matches the op model's "a tab that reaches 0 is dropped and
later tabs shift left" (ruling 3) and its refusal of a `setTabs` that STATES a zero
(`[1, 0, 1]` is `tab_invariant`).

### Patch 3: the owner banks are flushed on every path that leaves the process

Anchor: `process.exit(0)` in `World.processShutdown` and `process.exit(1)` in `cycle()`'s catch
(`src/engine/World.ts`), plus the `World.cycle` wrapper Patch 2 installs.

**The guarantee: a shutdown that saves the `.sav` files also persists the owner banks.** The
periodic flush is `World.currentTick % 100 === 0` inside `afterCycle`, and neither exit ever
reaches it. `processShutdown()` runs INSIDE `cycle()` - after `processCleanup`, before the
wrapper's `afterCycle()` - and calls `process.exit(0)` as soon as the last player is out, having
logged everyone out (which writes every `.sav`) on the way; the `process.exit(1)` in `cycle()`'s
own catch is the same shape. Without this patch a withdrawal made in the last minute before a
`::reboot`, a `docker compose restart` or a deploy was written into the character's `.sav` while
the items were still in the bank file too - **duplicated**; a deposit in that window was in
neither - **destroyed**.

Two halves, deliberately overlapping:

- **`process.on('exit', flushBanks)`**, registered by `installIdlescape`. It covers BOTH exit
  codes and anything else that ends the process cleanly, and it is legal only because
  `OwnerBankStore.flush()` is synchronous `fs` end to end (`writeFileSync` + `renameSync`,
  `src/idlescape/ownerBankFile.ts`): an `exit` handler may not await anything. It cannot cover a
  `SIGKILL` or a hard crash, which is what the periodic flush and `apply`'s write-before-return
  are for. A `SIGINT` or `SIGTERM` (`docker compose restart`, a deploy, Ctrl-C) is covered by
  both halves rather than neither: upstream's `src/app.ts` answers those signals with
  `World.rebootTimer(0)`, so they land on exactly the shutdown path above.
- **`beforeCycle()`**, called by the `World.cycle` wrapper BEFORE `originalCycle()`, flushes
  whenever `World.shutdown` is true. That is every tick from the one `::reboot` names onwards,
  so the state is already on disk before the tick that exits even begins. Belt to the exit
  handler's braces, and the half that is testable without ending the test process.

`flushBanks()` swallows and logs a throw rather than propagating it: a bank file that cannot be
written must not turn a graceful shutdown into a crash, and on the `cycle()` catch path the
process is already exiting on an error. `src/idlescape/installSweep.test.ts` pins all three
properties (the hook is registered and writes a dirty owner, a shutdown tick flushes before the
cycle, a throwing flush does not escape).

### The module graph: `install.js` must ROOT it

The engine's module graph is circular - `World` -> `PlayerLoading` -> `NetworkPlayer` ->
`Player` -> `World` - so a module reached part-way round the cycle sees bindings that are still
in their temporal dead zone. Two separate orders follow from that, and both are load-bearing.

**1. `install.js` must be the module the graph is rooted at.** Only the root is guaranteed to
run its body after every one of its imports has finished evaluating, and `install.ts`'s body
reads `Player` and `World` as values (it patches `Player.prototype.getInventory` and binds
`World.cycle`). That is why the replaced `src/app.ts` imports `#/idlescape/install.js` first,
before `fs`, and why `src/idlescape/install.test.ts` imports `./install.js` first as well. Let
something else root the graph and this body runs mid-cycle. Probed with the overlay applied:

```sh
npx tsx -e "import '#/engine/World.js'"   # ReferenceError: Cannot access 'Player' before initialization
                                          #   at installIdlescape (src/idlescape/install.ts, the Player.prototype patch)
```

`World.js` is reached before `Player.js` finishes because `PlayerLoading` now imports
`ownerBanks` from `install.js`, so opening the cycle at `World.js` pulls `install.ts` in from
inside `World` -> `PlayerLoading`'s own evaluation.

**The earlier note in this file that "only `World.js` is a safe entry" was wrong**, and
self-contradictory with the paragraph that followed it: `World.js` is precisely the entry that
breaks the overlay. It is also not true that every other entry throws - `PlayerLoading.js`
roots the graph cleanly, both in a pristine clone and with the overlay applied (`npx tsx -e
"import '#/engine/entity/PlayerLoading.js'"` succeeds, and with the overlay it prints the
overlay's own boot line), because it imports `NetworkPlayer.js` at line 2 and so forces
`Player` and `World` to complete before it reaches `install.js` at line 7. That is an accident
of import order, not a rule to rely on: the rule is that `install.js` roots the graph.

**2. Inside `install.ts`, `#/engine/World.js` is imported before `#/engine/entity/Player.js`**,
out of the alphabetical order the rest of the overlay follows. Making `Player.js` the module
that opens the cycle evaluates `NetworkPlayer`'s `extends Player` while `Player`'s class
binding is still dead. That failure is upstream's and predates the overlay: `npx tsx -e "import
'#/engine/entity/Player.js'"` throws `ReferenceError: Cannot access 'Player' before
initialization` at `NetworkPlayer.ts:38` in a pristine clone too.

Both orders are pinned by comments at the import sites. `PlayerLoading` only ever calls
`ownerBanks()` inside `load()`, never at module scope, so the partially-evaluated `install`
namespace it sees during the cycle is enough (the export is a hoisted function declaration).

**The standalone login worker (`src/login.ts`) is not affected.** It reaches the engine through
`LoginServer.ts`, whose `import Player from '#/engine/entity/Player.js'` looks like the hazard
of rule 2 but is used only as a type annotation, so `tsx`/esbuild elides it and the first
engine module actually evaluated is `#/engine/entity/PlayerLoading.js` - a clean root, as
above. Verified by probe on the pristine clone and with the overlay applied. It is unreachable
in this deployment anyway: `src/app.ts` only spawns that worker when `Environment.easyStartup`
is set, and the dev `world.json` sets neither `easyStartup` nor `login.enabled`.

### Packing a config the 2004 cache does not have: `tools/pack/BuildOverlay.ts`

`tools/pack/BuildOverlay.ts` is a new overlay file that sets `Environment.build.verify = false`
on the loaded config object and then calls `packAll`. The upstream escape hatch is
`BUILD_VERIFY=false`, but this world is configured by `data/config/world.json`, and
`loadWorldConfig()` returns as soon as that file exists: it never reads the `BUILD_*`
environment variables at all. Setting the flag here is the same switch applied where this world
can reach it, and it leaves the dev `world.json` untouched.

**What that one flag turns off, most consequential first.**

**1. Pack-ID pinning enforcement.** `validateConfigPack` (`tools/pack/PackFile.ts`) aborts on a
config name with no ID line only `if (Environment.build.verify)`; with the flag off it instead
auto-registers the name at `pack.max++` and REWRITES `<srcDir>/pack/<type>.pack`. That is the
one path from this tool to obj-id corruption: the ids in those files are the ids already
written into every `.sav` bank and every owner-bank JSON file, so a renumbering silently turns
one item into another. `BuildOverlay.ts` therefore sha256s every `engine/content/pack/*.pack`
before and after `packAll` and exits non-zero, naming the files that moved, if any of them did.
A clean run prints `pack ids unchanged (30 pack file(s) verified byte-for-byte)`. A run that
does not is a content change that needs an ID line added to `content-custom/pack/*.pack` by
hand, not a pack to ship. A `packAll` that THROWS exits at the tool's catch, before the
comparison runs, so a half-finished run is reported as a pack failure and its files are not
named. The two functions live in `tools/pack/packGuard.ts` so they can be unit tested without
running a pack (`src/idlescape/packGuard.test.ts` covers removed and rewritten files, the generated
packs a fresh clone gains without tripping it, the non-`.pack` files it ignores and a missing
directory). A pack that did not exist before the run is not a rewrite: the first image build (2026-09-08)
showed that a fresh Content clone has none of the eleven packer-generated packs, so `packAll`
creating them is the pack working, not a renumber.

**2. The 2004 authenticity CRC.** `readConfigs` (`tools/pack/config/PackShared.ts`) checks every
packed CLIENT config against a hard-coded CRC of the original cache - `703279713` for `.varp` -
so the moment `content-custom` adds `banktab_size_1..9` the pack aborts with
`.varp checksum mismatch!`. Relaxing that cannot ship a client-incompatible cache: the client
validates against the CRC table the SERVER advertises, not against the 2004 one. What it does
cost is a content drift the CRC would otherwise have caught, which is why `npm run build` stays
the tool for anything that is not an overlay pack.

The ids themselves are pinned by content. `content-custom/pack/varp.pack` is a copy of
upstream's with nine lines appended (`359=banktab_size_1` .. `367=banktab_size_9`), so they are
the same on every machine rather than whatever order a crawl happened to auto-assign. Since entry
3's Task 4, `content-overlay.ps1 -Check` hashes the pristine upstream BLOB at the clone's HEAD
rather than the working-tree file the overlay has already overwritten, so that entry reports no
drift after an apply and the check exits 1 when there is real drift. The recorded hash is
recoverable with
`git -C engine/content -c core.autocrlf=false show HEAD:pack/varp.pack | sha256sum`.

Pack after any content-overlay change:

```sh
powershell -File scripts/content-overlay.ps1
cd engine/server && npx tsx tools/pack/BuildOverlay.ts
```

`scripts/setup.ps1` runs it in place of `npm run build` for the same reason.

## Owner bank semantics

The op model in `src/idlescape/types.ts`, the tab and slot arithmetic in
`src/idlescape/bankLayout.ts` (the engine-side counterpart of `web/src/bank/layout.ts`) and the
pure `applyOps` in `src/idlescape/ops.ts`, which re-exports `tabRanges` so callers have one
entry point (Task 7). `src/idlescape/ops.test.ts` pins every ruling below against the packed cache and the
engine's real `Inventory` (inv 95, 240 slots, always-stack). Em dashes in the source rulings are
written as hyphens here, per the project's naming rule; nothing else is changed.

1. **Tab invariant.** `tabs.length <= 9`; every size is `>= 1`; `sum(sizes) <= lastUsedSlot(inv)`.
   SP8b says "sum ≤ used slots"; a 274 bank is not required to be hole-free (a withdrawal
   leaves a gap), so "used" is read as *the highest occupied slot index + 1* - the OSRS
   meaning of "tabs cannot extend past the items". A `setTabs` that breaks it is rejected
   whole with `tab_invariant`; the batch is atomic.
2. **Insert across a tab boundary.** `insert` moves one slot and shifts the rest; if `from`
   and `to` fall in different tab ranges the op is rejected with `tab_invariant` unless the
   same batch also carries a `setTabs` that makes the move legal (order matters - the batch
   is applied in sequence and validated after every op).
3. **Empty tabs.** After each op, any tab whose size reaches 0 is dropped and later tabs shift
   left, exactly as OSRS does.
4. **`sort by: 'value'`** uses the engine's only price signal, High Alchemy
   (`max(floor(ObjType.cost * 6 / 10), 1)`, verified against `alchemy.rs2:25`). SP9 can pass a
   market price map later; the engine never guesses one.
5. **`delta`.** `{ op: 'delta', obj, count }`; the spec's `{ obj, delta }` shorthand is
   accepted by `normaliseOp` and normalised to it. A negative count that exceeds the held
   amount fails with `insufficient` and rolls the batch back; a positive count that does not
   fit fails with `full`. Nothing is ever dropped on the floor (unlike `INV_ADD`).

### What the rulings leave open, and what Task 7 decided

- **Ruling 4's formula is confirmed.** `engine/content/scripts/skill_magic/scripts/spells/alchemy.rs2:25`
  is `def_int $profit = max(scale(6, 10, oc_cost($item)), 1);`, `SCALE` is `(a * c) / b`
  (`src/engine/script/handlers/NumberOps.ts`), and every script push goes through
  `toInt32` = `num | 0` (`src/util/Numbers.ts`), which truncates toward zero and therefore
  equals `Math.floor` for a non-negative `cost`. So `max(floor(cost * 6 / 10), 1)` is the
  engine's own arithmetic, not an approximation of it.
- **"A `setTabs` that makes the move legal" (ruling 2) is a real check, not a flag.** `applyOps`
  tracks two layouts: `arranged`, the sizes the items currently sit in, and `declared`, the
  sizes a `setTabs` earlier in the batch asked for. An `insert` is legal exactly when taking one
  slot out of `from`'s tab in `arranged` and adding it to `to`'s tab in `declared` turns the
  first into the second. With no `setTabs` the two are equal and this reduces to "`from` and
  `to` are in the same tab", so a lone cross-tab insert is still refused; a `setTabs` that moves
  the sizes the wrong way (`[3, 1]` for a move out of tab 1 into tab 2) is refused too.
- **`sort` and `delta` shrink the tabs instead of failing.** Both can lower the used-slot count
  without the caller asking for a layout change (`sort` compacts the holes inside its range, a
  negative `delta` empties slots), and ruling 1 would then reject an operation the owner is
  entitled to. Ruling 3's "a tab that reaches 0 is dropped" is therefore generalised for those
  two ops only: the sizes are clamped down onto the items, last tab first, and empties dropped.
  The three ops that *state* a layout (`setTabs`, `insert`, `moveToTab`) are still rejected
  whole with `tab_invariant` when they break it.
- **A zero tab size is a bad request, not an empty tab to collapse.** Ruling 3 drops a tab whose
  size *reaches* 0 through a move; ruling 1 says every size is `>= 1`. So `setTabs` validates the
  sizes exactly as the caller sent them (`[1, 0, 1]` is `tab_invariant`), and only the ops that
  arrive at a 0 by moving an item out of a tab collapse it.
- **`swap` across tabs is allowed on purpose; `insert` across tabs is not.** A swap exchanges two
  slots in place, so each tab keeps the same number of slots and the same occupancy, and dropping
  an item into an empty slot of another tab is a deliberate, unambiguous move. An `insert`
  shifts every slot between its ends, so crossing a boundary drags unrelated items into a
  neighbouring tab: that needs the `setTabs` of ruling 2 to say what the sizes become.
- **`moveToTab` to a tab past the last one creates it** (SP8b's "dropping on + creates a new
  tab"), and `tab: 0` appends the item to the main tab at the last used slot. A `moveToTab` onto
  the tab the slot is already in is a no-op and reports `changed: false`.
- **An obj the pack has never heard of never throws.** `ObjType.get` is a bare array index, so an
  id at or past `ObjType.count` (a bank written by an older pack, or a hand-edited store file)
  comes back undefined. `sort` treats such an obj as value 0 and name `''`; a `delta` naming one
  is refused with `bad_op`, by `normaliseOp` and again inside `applyOps`, because
  `Inventory.add` would dereference it.
- **A move cannot place an item past the last one in the bank.** Both ends of a `swap` and of an
  `insert` are pinned to the highest occupied index (`lastUsedSlot` - 1), so a move can only
  permute the used region, never stretch it out to slot 239 with holes behind it. A slot outside
  the container is still `bad_slot`; this only folds a legal but empty destination back onto the
  items, the way OSRS refuses to drop an item past the end of the bank.
- **`changed` is measured, not counted.** `applyOps` compares the items and the tabs it ends with
  against the ones it started from, so a batch that cancels out (a swap of a slot with itself, a
  sort of an already sorted tab, a `setTabs` restating the current sizes) reports
  `changed: false` and the store does not burn a version on it. `sort by 'name'` compares with
  `localeCompare(other, 'en')` so the order does not depend on the host's locale.
- **Correction to the Task 7 brief's test fixture.** The brief's "a tab emptied by moveToTab"
  case expected `tabs: [1]` from `applyOps(bank, [1, 1], [{ op: 'moveToTab', slot: 0, tab: 2 }])`.
  That drops the emptied tab 1 but forgets to grow tab 2 by the item it received; the correct
  result is `[2]`, which is also what the brief's own reference implementation produces and what
  its sibling case (`[2, 2]` + `moveToTab slot 3 -> tab 1` = `[3, 1]`) implies. The test asserts
  `[2]`. The brief's sort fixture also used obj `4151`, which this pack does not have
  (`ObjType.count` is 3894); the fixture uses `1618`/`1619`/`995`, three distinct costs, so the
  value order is neither the id order nor the name order.

### The store: `src/idlescape/ownerBank.ts` (Task 8)

`OwnerBankStore` owns one `Inventory` per Firebase uid plus its tab layout, version, migration
list and persistence. One JSON file per owner, `<bankDir>/<ownerKey>.json`, shape
`{ version, tabs, slots, migrated }`; `slots` is sparse (empty slots are absent).

- **One live container per owner.** `get(ownerKey)` returns the store's own `Inventory`, never a
  copy, so every character of an account that is online shares the same object and an engine
  script writing to it is writing to the bank. Nothing else in the class hands the container
  out; `snapshot()` and the file writer build fresh DTOs from it.
- **`apply` bumps the version synchronously** (dispatch ruling 2). The number it returns is the
  new one, and the file is written before it returns, so an owner with nobody online cannot
  lose an external change to a crash. `expectedVersion` is optimistic concurrency: a mismatch
  answers `{ ok: false, reason: 'conflict', version }` and changes nothing; `null` forces.
- **A batch that changes nothing burns no version.** `applyOps` measures `changed`, so an empty
  batch, a swap of a slot with itself or a `setTabs` that restates the sizes returns
  `{ ok: true, version }` with the CURRENT version and writes no file. A tab change still
  pending from `setTabs` stays pending rather than being marked persisted.
- **`ApplyOutcome` carries one store-level refusal, `{ ok: false, reason: 'unavailable' }`**
  (additive to the `BankApplyError` reasons; Task 10/11 map it to a 503). It means persistence
  for that owner is suspended - see the quarantine ruling below - and `apply` returns it before
  it even reads the ops, so an unpersistable change never reaches the container.
- **`apply` records the tabs `applyOps` RETURNS** (Task 7 carry), not the ones it passed in:
  `sort` and `delta` clamp the tabs onto the items and empty tabs are dropped, so the returned
  array is the layout that is stored, persisted and reported by `snapshot()`.
- **`apply` does not reset the container's tracking**, because an online client still needs the
  `inv_transmit` diff for the change, and the sweep runs after `processClientsOut` has written
  it. It sets a one-shot `appliedExternally` flag on the entry instead, and `bumpDirty()`
  consumes that flag - resetting the tracking, marking the file dirty, clearing `tabsChanged` -
  rather than bumping the version a second time. **This is a change from Task 8's behaviour**,
  which bumped again: a web client that echoes back the version `apply` just handed it would
  otherwise get a guaranteed 409 on every item-moving op (`swap`, `insert`, `moveToTab`,
  `sort`) forever, while a `setTabs`-only batch (which never touches `inv.update`) was never
  double-bumped. The two shapes now behave identically, which is what SP8b has to be written
  against. **The trade-off**: a RuneScript change landing between the apply and the next sweep
  is folded into the apply's version rather than getting one of its own. The sweep genuinely
  cannot tell the two changes apart, `dirtyFile` still carries the in-game change to the next
  `flush()`, and folding matches the sweep's existing "everything since the last observed
  version" model - a reader that refetches at the apply's version sees both changes. An in-game
  change in any LATER tick bumps normally. Versions only ever increase.
  (Do not implement this with a `bumpedAtTick` comparison: `World.currentTick` is incremented
  inside `cycle()` before the overlay's `afterCycle()` runs, so such a comparison can never
  fire.) The flag has one consequence beyond the version: because the sweep no longer bumps for
  an external change, it also no longer self-corrects a stale in-game TAB layout for that owner,
  so the post-cycle hook consults `externallyApplied()` and pushes the store's layout out for
  that one tick instead of reading the character's varps in - see Patch 2 above.
- **`externallyApplied()` reports the armed owners without disarming them.** It exists for that
  push-out decision only; `bumpDirty` stays the single consumer of the flag, so nothing else can
  accidentally swallow an apply's dirt. **ANY apply arms it**, not only one that touched the
  tabs: the flag is on the entry, not on the tab array, so an item-only `delta` also puts the
  owner in push-out mode for the next tick, and a caller applying on most ticks holds it there
  continuously (the cadence note in Patch 2 above).
- **The ruling on a same-tick collision: the web caller wins.** An in-game tab drag made in the
  same tick as an external apply is discarded, because the web caller holds a version number for
  its change and expects it to stick, while the player holds nothing, sees the tabs snap back
  within a tick and can simply drag again - which the next tick mirrors in normally. The item
  change behind an in-game action in that tick is NOT discarded: it lands in the shared container
  and is folded into the apply's version, per the bullet above. Only the tab layout is resolved
  by this ruling.
- **`bumpDirty()` is the tick sweep** (Task 9 calls it from the post-cycle hook, after client
  output): one bump and one dirty mark per container reporting `update` or a changed tab
  layout, then `resetTracking()`. Upstream's `processCleanup` only resets `player.invs`, and an
  owner bank deliberately lives outside those maps, so this is the only thing that resets it.
- **`setTabs` marks the owner dirty as well as changed**, so a bare tab rearrangement with no
  item change behind it is still durable at the next `flush()`.
- **`flush()` writes only dirty owners**, atomically: `writeFileSync` to `<ownerKey>.json.tmp`
  then `renameSync` over `<ownerKey>.json`, so a crash never leaves a half-written bank. That
  write, the file READ (`readBankFile`, which also reports what it had to drop), the sparse
  `slots` shape and the `.corrupt` quarantine name live in
  `src/idlescape/ownerBankFile.ts`, and the two pure helpers behind `migrate` in
  `src/idlescape/ownerBankMerge.ts`. Both were split out of `ownerBank.ts` purely to keep it
  under the project's 400-line limit; the store's exported surface is unchanged and nothing
  outside `ownerBank.ts` imports either module.
- **`OWNER_KEY_RE` = `/^[A-Za-z0-9_-]{1,64}$/`**, checked by every public method BEFORE any path
  is built, so `..`, separators and spaces never reach the filesystem.
- **A corrupt bank file never takes the world down.** `get()` moves the unreadable file to
  `<ownerKey>.json.<ISO timestamp>.corrupt` (colons replaced, Windows forbids them in a path;
  a counter suffix covers two corruptions inside one millisecond), logs it, and answers with an
  empty container at version 0, so the owner can be restored by hand instead of being silently
  overwritten. The timestamp matters: a fixed `.corrupt` name would let a second corruption
  overwrite the very copy the owner would be restored from. A file that parses is still
  field-by-field re-validated by `readBankFile` (`src/idlescape/ownerBankFile.ts`): bad slots,
  non-positive counts, obj ids outside this pack and out-of-range tabs are dropped.
- **A partial loss suspends writes too, and is never silent.** `readBankFile` COUNTS the slots
  it refused, and the store treats a non-zero count exactly as it treats a failed quarantine:
  one `warnOnce` naming the owner, the count and the path, and `entry.noWrite`. Without that a
  file that is valid JSON but partly bad loaded short and the very first `writeEntry` rewrote it
  without those slots, making the loss permanent with nothing in the log to say so. In-game play
  continues against the (short) container; only the file is left alone, until an operator fixes
  or moves it.
- **If the quarantine rename itself FAILS, writes for that owner are suspended.** The file that
  could not be moved is the owner's only surviving bank, and the container being served is
  empty, so `entry.noWrite` is set: `writeEntry` and `flush` return early (leaving `dirtyFile`
  set, so nothing pretends the change reached disk), `apply` answers `unavailable`, and
  `migrate` answers `'refused'` (the `.sav` bank stays the source of truth for that character).
  In-game play still works against the in-memory container and `bumpDirty` still moves the
  version; only the file is left alone, until an operator clears it.
- **`migrate(ownerKey, username, objs)` merges a character's legacy `.sav` bank exactly once**,
  tracked by the `migrated` list. The first character keeps its slot order; later characters
  are appended, stacking where the container allows and filling holes otherwise. Dispatch
  ruling 4: a merge that cannot complete is refused WHOLE - it runs against a scratch container
  first, so nothing is written, the username is NOT recorded and the `.sav` stays the source of
  truth, with one log line per owner/character. Three things refuse it: the bank does not fit,
  it names an obj id this pack does not have (the same `0 <= obj < ObjType.count` guard the
  file reader applies, so the container can never hold an id the file would then silently
  drop), or the owner has writes suspended.
- **`migrate` answers `'merged' | 'already' | 'refused'`.** Only `'merged'` says the items are
  now in the owner store, and no outcome lets a caller retire, clear or rewrite a character's
  `.sav` bank. The other two are separate outcomes because the caller has to act differently:
  `'already'` means the store is authoritative for this character and its `.sav` bank is stale
  leftovers, while `'refused'` means the `.sav` is the ONLY copy and `PlayerLoading` must keep
  it alive by writing it back into that character's own container (PlayerLoading hunk 3). A
  boolean folded the two together, and the refusal path then lost the bank at the next autosave.
  A refusal is retried at every login until it fits.
- **`evict(keep)` never drops an owner with unsaved work**, whatever the predicate says: a
  container that is dirty on disk, dirty in memory or holds an unsaved tab change is held back,
  and so is one whose writes are suspended (`noWrite`) - explicitly, by its own check, not
  incidentally through `dirtyFile`. Dropping a suspended entry would re-read the same unusable
  file at the next `get()`, warn again and start the suspension over; it stays for the life of
  the process.

## Management routes (`src/idlescape/management.ts`, Task 10)

The seam the front server owns the economy through (spec section 7). Registered on the
MANAGEMENT Fastify app only, never on the game web app.

| Route | Body | 200 | Errors |
|---|---|---|---|
| `GET /owner/:key/bank` | - | `{ ownerKey, version, capacity, tabs, slots }` | 400 `bad_key`, 401 `unauthorised` |
| `POST /owner/:key/bank/apply` | `{ expectedVersion, ops }` | `{ ownerKey, version }` | 400 `bad_key` / `bad_ops`, 401 `unauthorised`, 409 `{ error: 'version', version }`, 422 `{ error: <BankApplyError> }`, 503 `{ error: 'unavailable' }` |
| `GET /owner/health` | - | `{ ok: true }` | 401 `unauthorised` |

`GET /owner/health` touches no store: it exists so `HealthSnapshot.management` on the front server
can prove at runtime that the deployed image carries this overlay, that the management link
resolves, and that both halves hold the same `ENGINE_MANAGEMENT_SECRET` (decision D75). Its three
possible answers are the whole field: 200 is `up`, 401 is a secret mismatch, and 404 is an engine
that started with no secret at all, which registers none of these routes.

- `expectedVersion` may be absent or `null` to force; any other value must be a non-negative
  safe integer. `ops` is an array of at most 200, each one shaped by `normaliseOp`.
- **503 `unavailable`** is the store's own refusal (`ApplyOutcome.reason === 'unavailable'`): the
  owner's bank file could not be read and could not be quarantined, so writes for that owner are
  suspended. It is not a `BankApplyError`, it is not the caller's fault and no different batch
  of ops would succeed, which is why it is not a 422. The front server
  (`server/src/engine/managementClient.ts`) maps 200/409/422+400/503 onto
  `ok` / `conflict` / `rejected` / `unavailable`, and reads anything else as `unavailable` too.
- **Authentication**: `x-idlescape-mgmt` must equal `idlescapeConfig.managementSecret`, compared
  with `timingSafeEqual` over UTF-8 BYTES (a non-ASCII header is a clean 401, never a length
  throw turned into a 500). The secret comes from `ENGINE_MANAGEMENT_SECRET` - the SAME env name
  the front server reads (`server/src/env.ts`), exported into the engine process from
  `server/.env` by `scripts/start-stack.ps1` - or from `managementSecret` in
  `data/config/idlescape.json`. It is never logged and never echoed in a body.
- **With an empty secret none of the three routes is registered at all**, so a misconfigured
  world answers 404 rather than exposing an unauthenticated economy seam. Registration logs one
  warning naming the missing variable, never a value.
- **The owner key is validated (`OWNER_KEY_RE`) before the store is touched**, on both bank
  routes: it becomes a file name.
- **`apply` runs synchronously inside the handler.** Nothing is awaited between reading the
  version and mutating, and the engine is single-threaded with a synchronous `World.cycle`, so
  the handler necessarily runs BETWEEN ticks. That is the atomicity the spec's "applied on the
  world tick" asks for, with no queue to drain.
- A successful apply posts `notifyBankChanged` (the in-game path is covered by `afterCycle`'s
  sweep instead). A conflict, a rejection and an `unavailable` post nothing.
- **The change hook is signed with the MANAGEMENT secret** (`notifyBankChanged`,
  `src/idlescape/install.ts`). The front server's `/internal/bank-changed` verifies
  `x-idlescape-mgmt` against `ENGINE_MANAGEMENT_SECRET` (`server/src/bank/routes.ts`), which
  `server/src/env.ts` holds to at least 32 characters, so it can never coincide by accident
  with `OWNER_ASSERTION_SECRET`: Task 10 shipped signing it with `idlescapeConfig.ownerSecret`,
  which 401ed on every post. The hook is also silent when EITHER half of its configuration is
  missing - no `hookUrl` is the dev world, no `managementSecret` would post an unsigned request
  the front server can only refuse - so a misconfigured world is quiet rather than noisy.
  `src/idlescape/install.test.ts` pins both. The WIRE FORMAT itself is pinned from the other
  side by `server/src/bank/hookContract.test.ts`, which builds the request exactly as
  `notifyBankChanged` does - same header name, same body shape, the management secret - and puts
  it through the real `handleHook`, plus the wrong-secret 401. The two packages cannot import
  each other, and before that test both halves passed against their own fakes while disagreeing
  with each other, which is how Task 10's bug survived.

### The `/setup*` guard (`registerSetupGuard`)

Upstream's management app also carries `GET /setup`, `GET /setup/config` and `PUT /setup/config`,
none of which had any authentication. `GET /setup/config` returns `loadWorldConfig()` whole,
`db.pass` included; `PUT /setup/config` rewrites `node.production` and `build.verify`. Audit C07.

`registerSetupGuard(app, secret)` adds ONE `onRequest` hook that 401s any request whose path is
`/setup` or starts with `/setup/`, using the same `authorised()` constant-time check as the bank
routes. It matches on the path only, so `/setup/config?x=1` cannot slip past a prefix test. It is
registered in `src/web.ts` above the routes it guards, so it does not depend on route order.

- `/prometheus` is deliberately NOT matched: `server/src/health.ts` polls it for the players gauge
  and it carries no secret.
- With an empty secret `authorised()` refuses everything, so a world with no
  `ENGINE_MANAGEMENT_SECRET` loses the setup page entirely and `data/config/world.json` is edited
  directly. That is the same thing an empty secret already does to the bank routes, except that
  the guard answers 401 where an unregistered route answers 404.
- The refusal body is `{ error: 'unauthorised' }` and never names or echoes what it was guarding.
- The guard makes the setup page curl-only, not merely secret-gated. A browser navigation cannot
  attach a custom request header, and upstream's `view/setup.ejs` fetches `/setup/config` from the
  page with no header of its own, so with the guard in place nobody edits a world through the UI in
  any deployment, secret or not. `data/config/world.json` is how a world is changed;
  `curl -H "x-idlescape-mgmt: <secret>" .../setup/config` is how it is read back. Losing a UI we
  never used is the whole point: the routes behind it hand out `db.pass` and rewrite
  `node.production`.
