## Traps recorded

- **setup.ps1 non-force checkout on re-pin.** 274's pack regenerates tracked build artifacts (`public/client/{bzip2,client.js,tinymidipcm}.wasm/js`), leaving the tree dirty after a clone; a plain `git checkout -q $sha` then throws on any later unattended re-pin. Only worked in Task 1 because the implementer manually cleaned first. Fixed with `git checkout -q -f $sha`.
- **Bun's built-in WebSocket can't set an Origin header.** The relay's `openUpstream` used it to reach the 274 engine; 274 enforces `allowedOrigin` on the `/` WS upgrade and silently 502s any relayed connection with no matching Origin. This is load-bearing for prod (allowedOrigin is required there) and was invisible in Task 4's smoke test only because allowedOrigin was temporarily emptied to get a green run. Fixed in Task 4b by switching to the `ws` npm package and forwarding an Origin.
- **Browser-Origin forwarding is a trap of its own.** Task 4b's fix (forward whatever Origin the browser sent) only works when the browser talks to the front server directly on its allowedOrigin port (8787). It silently breaks interactive dev through Vite (:5173), because the Vite proxy forwards its own Origin without `changeOrigin`, and :8787 itself has no build in dev. Discovered only at final review, not before — the acceptance e2e's green result was origin-coincidental (it hit a built web/dist on 8787 directly), not proof the login path worked generally. Fixed by forwarding a configured `env.publicOrigin` instead of the raw browser Origin.
- **Dev proxy config can drift silently from the route table it's meant to mirror.** `vite.config.ts`'s proxy regex is a hand-maintained mirror of `CACHE_PREFIXES` in `types.ts`; Task 2 updated the latter (dropped `/models`, added `/versionlist`) but nothing forced the former to follow, and nothing caught the drift until the final review's manual read-through.
- **A stale 4h resume cron (156d3faa) fired mid-session** describing the project as still at the retrofit stage, well behind actual progress (SP1b Tasks 1-7 already done). The session judged the ledger over the cron's description and proceeded from real state, per the cron's own "trust the ledger" instruction. Cron was one-shot and auto-deleted; recorded here only as a process note, not a code trap.
