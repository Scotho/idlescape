# SP1b — Revision 274 Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the pinned engine, content, and client-fork from Lost City build 225 to build 274, adjust the scripts and front server for 274's runtime and asset delivery, re-apply our client hooks on the 274 client, and add a custom-content overlay mechanism — without changing the shell's behaviour or touching the live 225 PoC.

**Architecture:** 274 runs the engine on Node 24 via `tsx` with a Fastify web layer and `data/config/world.json` instead of `.env`; some cache routes gain a CRC suffix and a `/versionlist` route, and models/animations/maps/music stream over a second WebSocket (OnDemandWorker) on the same `/` upgrade. Our front server (Bun) keeps its role but its router/proxy/relay adapt to those routes; the client fork rebases to 274 and re-applies the Task 9/10 hooks; a `content-custom/` overlay lets us add content while the Content clone stays pinned and pristine.

**Tech Stack:** Node 24 + `tsx` (engine, per 274 upstream), Bun 1.4 (front server + client build), TypeScript strict, `bun test` (server, client hooks), Playwright (web e2e), Java 17+ (pack tools).

**Spec:** `docs/superpowers/specs/2026-09-05-sp1b-revision-274-design.md` (roadmap: `docs/superpowers/specs/2026-09-05-idlescape-roadmap-and-handoff.md`)

## Global Constraints

- Engine and content under `engine/` are upstream clones pinned in `scripts/upstream.lock`; extractors/adapters read them, no file inside them is hand-edited. The client fork under `client/` IS ours to edit (hooks only; the rest is a vendored tree tracked as plain files with upstream history in `client/.upstream-git`).
- The LIVE PoC (`live/`, 225, Bun) on 8888/43594/8898 is frozen and untouched. SP1b migrates only the SDD tree (`engine/`, `client/`). Local dev/e2e ports: front server 8787, dev engine web 8899, game 43596, management 8897, emulators auth 9099 / firestore 8080.
- 274 engine runtime is Node 24 + `tsx` (NOT Bun); the front server and client build stay Bun. Node 24 and Bun 1.4 are both installed; Java 21 present for the pack.
- The exact 274 config keys, cache routes, `view/client.ejs` query params, and `bundle.ts` outputs are NOT hardcoded in this plan — the implementer READS them from the pinned 274 clone and adapts, recording what was found. The plan is concrete about OUR code (front server, hooks re-apply, scripts, overlay) and prescriptive-by-reference about upstream.
- TypeScript strict, no new `as any`; files under 400 lines (excluding vendored client tree and `client/out`); conventional commits; `types.ts` per package.
- Vendored/upstream changes are logged: `client/PATCHES.md` lists every hook call-site hunk; `CREDITS.md` stays current.
- Deploy stays controller-gated; nothing in this plan deploys or touches Firebase cloud resources.

### Task 4b: Front-server relay forwards Origin to the 274 engine

**Files:**
- Modify: `server/src/proxy/ws.ts` (openUpstream + relay wiring), `server/src/index.ts` (pass the browser Origin into openUpstream), `server/package.json` (add `ws` dep), `server/src/proxy/ws.test.ts`, `server/src/router.test.ts` (drop the /client/bzip2.wasm ref)
- Test: `server/src/proxy/ws.test.ts`

**Interfaces:**
- Consumes: the current openUpstream/relayHandlers/RelayData; index.ts's `/` upgrade path which already reads `req.headers.get('origin')`.
- Produces: `openUpstream(engineWs, opts: { origin?: string })` using a header-capable WS client (the `ws` package) that sends the given Origin; the relay forwards the browser's Origin so the 274 engine (which rejects `/` upgrades when Origin != web.allowedOrigin) accepts the relayed socket.

Why: 274 `engine/src/web.ts` rejects the WS upgrade when `web.allowedOrigin` is set and the connection Origin differs. Our relay's upstream socket used Bun's built-in `WebSocket`, which sends no Origin and can't set one, so relayed logins 502 under any non-empty `allowedOrigin` (prod = https://osrs.scotho.com; dev = http://localhost:8787). This blocks Task 7's e2e and production.

- [ ] Step 1: Add `ws` (and `@types/ws`) to server/package.json; `bun install`.
- [ ] Step 2: Rewrite openUpstream to use the `ws` package's WebSocket with `{ origin, ... }` (subprotocol 'binary'), binaryType arraybuffer; accept an `origin` option and pass it. Preserve the SP1 behavior: resolve on open, reject on error/timeout (~5s), the early greeting buffer (`early: ArrayBuffer[]`) captured before resolve, and per-connection isolation. Adapt the relay's upstream event wiring (relayHandlers.open) to the `ws` client API (its message frames arrive as Buffer — toBytes already handles Buffer/Uint8Array; confirm), keeping the drain-early-then-attach-live ordering and safeCloseCode mirroring.
- [ ] Step 3: index.ts: capture the incoming `/` upgrade request's `Origin` header and pass it to openUpstream so the upstream socket carries the browser's Origin.
- [ ] Step 4: Test (ws.test.ts): a fake engine that REJECTS the upgrade unless the connection Origin equals a configured allowedOrigin; assert the relay, given a browser Origin matching it, connects and relays; and (regression) the greeting buffer + two-socket + close-code tests still pass. Also drop the stale `/client/bzip2.wasm` reference in router.test.ts (274 dropped that wasm).
- [ ] Step 5: Restore dev `world.json` `web.allowedOrigin` to `http://localhost:8787` (setup.ps1 already writes this; ensure the current engine/server/data/config/world.json is NOT left with an empty allowedOrigin from Task 4's smoke). Run `cd server && bun test` (start the Firestore emulator for the pair/bridge suites or note them as emulator-dependent).
