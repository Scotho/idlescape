# Phase A findings — engine account, character, bank, currency, item metadata and mutation APIs

Date: 2026-09-05. Scope: handoff sections 2.2, 5, 6.1, 6.2, 10.1, 13, 15, 19. Read-only audit of
`engine/server` (Engine-TS rev 274, pinned), `engine/content`, `server/`, `client/src/hooks`, `firebase/`.
"Verified" = read in code at the cited line. "Inferred" is marked as such.

## Summary

1. In our single-world config (`login.enabled=false`) the engine never touches the `account` table and never checks a password: a login is "username has a `.sav` file or not" (`LoginThread.ts:62-100`). `account_id` is hard-coded to 1. The username *is* the character identity.
2. The whole character (coords, stats, varps, inventory 93, worn 94, **bank 95**) lives in one binary file `engine/server/data/players/main/<username>.sav`; there is no bank table in Prisma. Saves happen on logout and every 1500 ticks (15 min); a crash loses up to 15 min of bank changes.
3. Our `server/src/bridge.ts` creates exactly one character per Firebase uid (`gameAccounts/{uid}` -> `{gameName, secret}`, `gameNames/{name}` -> `{uid}`). The `secret` is sent as the game password but the engine ignores it. Multi-character needs a new `characters` collection and per-character name allocation; no engine change is required for *creation*.
4. The bank is an ordinary per-player `Inventory` of type 95, size 240, `stackall=yes`, manipulated only by RuneScript (`inv_moveitem_cert/uncert`, `inv_movetoslot`) running on the owning player. The engine already has a `scope=shared` inventory kind that is world-global (`Player.getInventory` -> `World.getInventory`), which is the closest existing seam for a shared bank, but it is not keyed per owner.
5. Coins are obj 995, `stackable=yes`, `cost` defaults to 1; a stack caps at `0x7fffffff`. High alch = `max(floor(cost*6/10),1)`, low = `*4/10` (`alchemy.rs2:25,61`).
6. Item metadata (name, cost, stackable, tradeable, members, certlink) is in `engine/content/scripts/**/*.obj` + `pack/obj.pack`; `scripts/gen` referenced by SP3/SPW does not exist yet.
7. Hiscores: `hiscore`/`hiscore_large` are written only in `LoginServer.ts` (multiworld). Confirmed nothing else writes them. Wealth events (`wealth_event` op) exist but only persist to `session_wealth` when `logger.enabled` (false).
8. There is **no** HTTP/RPC path to mutate a player's inventory from outside: management port only serves `/prometheus` and `/setup`. The only external-ish hook is the friend server's `RELAY_QUEUESCRIPT` (queues a named `[queue,...]` script on an online player), plus staff `::give`/`::setvar` cheats over the game socket.
9. Because `world.json` has `node.production=false`, every player logs in with `staffmodlevel=4` and can run `::give coins 2147483647`. Any economy/wealth feature is meaningless until that is fixed.
10. Nothing in the engine or our server deletes a character today; deletion would be "remove `.sav` + Firestore docs" and is trivially implementable as a human-only route.

## Findings

### F1. Account model and single-world login (handoff 2.2, 6.1, 19)

- Prisma singleworld schema has 14 tables; `account` = `{id autoincrement, username @unique, password, registration_ip, registration_date, muted_until, banned_until, staffmodlevel, members}` (`engine/server/prisma/singleworld/schema.prisma:16-31`), `account_login` keyed `[profile, account_id]` (`:33-45`), `hiscore`/`hiscore_large` keyed `[profile, type, account_id]` (`:47-69`), `session`/`session_log`/`session_wealth` (`:93-135`). **No bank, inventory or item table** (verified by reading the whole schema).
- Our config: `engine/server/data/config/world.json` sets `website.registration=false`, `login.enabled=false`, `friend.enabled=false`, `logger.enabled=false`, `node.profile="main"`, `node.production=false`, `web.managementPort=8897`.
- Login path: `World.ts:2198-2221` decodes `uid`, `username`, `password` from the client packet (username 1-12 chars, password 1-20), then posts `player_login` to the login worker (`World.ts:2241-2253`).
- Single-world branch (`engine/server/src/server/login/LoginThread.ts:62-100`): if `data/players/<profile>/<username>.sav` does not exist -> `reply: 4, save: null, account_id: 1` (new character); else `reply: 0, save: <file bytes>, account_id: 1`. **No DB query, no bcrypt, password unused.** `staffmodlevel = 4` when `!Environment.node.production` (`:63-67`).
- Multiworld branch (only if `login.enabled`): `LoginServer.ts:196-227` selects `account` by username; when `website.registration=false` and no row exists it auto-inserts with `bcrypt.hashSync(password.toLowerCase(), 10)` (`:203-217`), then `bcrypt.compare` (`:227`). This is the "auto-registration on first login" the roadmap mentions — it is **not active** in our mode.
- New character bootstrapping: `PlayerLoading.load` with an empty save gives all stats 0 / level 1 except hitpoints 10 (`PlayerLoading.ts:39-51`); spawn coordinates come from the `[login]` trigger script (inferred; `Player.onLogin` runs `ServerTriggerType.LOGIN` at `Player.ts:525-527`).
- Duplicate login: a second socket for the same username is rejected with code 5 while the first is online (`World.ts:852-869`) or while its save is being flushed (`World.ts:811-822`); a `reconnecting` login (opcode 18) replaces the socket (`World.ts:825-850`).
- Our bridge (`server/src/bridge.ts:15-44`): `POST /api/bridge` verifies the Firebase ID token, reads `gameAccounts/{uid}`; if absent runs a transaction that allocates `gameName` (normalised desired name or random guest name, suffix retry up to 20, `gameName.ts:3,17-19,28`), `secret = randomSecret()` (20 chars, `gameName.ts:32`), and writes `gameAccounts/{uid} = {gameName, secret, createdAt}`, `gameNames/{name} = {uid}`, `users/{uid}.gameName` (`bridge.ts:34-37`, doc shape `types.ts:45-49`). Firestore rules make `gameAccounts` and `gameNames` server-only (`firebase/firestore.rules:29-30`) and forbid clients from setting `users/{uid}.gameName` (`:11,13`).
- The shell calls `window.idlescape.client.login(gameName, secret)` (`client/src/hooks/install.ts:15`, `web/src/main.ts:167`); the secret travels as the RS2 password and is ignored by the engine (F1 bullet 4). The `.sav` file is created lazily by the engine on first logout/autosave (`LoginThread.ts:121,142`), so "character exists" today == "gameAccounts doc exists", not "sav exists".
- Security note (verified): the WebSocket relay (`server/src/proxy/ws.ts`, `server/src/index.ts:46,67`) only checks the gate cookie; anyone behind the gate who knows a game name can log in as that character because the engine ignores the password.

### F2. Character persistence — the .sav file (handoff 19 "character persistence")

- Format `PlayerLoading.ts:11-12` magic `0x2004`, version 7, CRC32 trailer. Layout (`Player.save()` `Player.ts:190-262`, `PlayerLoading.load` `:68-161`): x, z, level, body[7], colors[5], gender, runenergy, playtime, 21x(stat xp int32 + level u8), varp count + `(id, varint)` for `scope=perm` non-zero varps, **inventory count + per inv `(type u16, capacity u16, capacity x (objId+1 u16, count u8 or 255+u32))`** for every `scope=perm` inventory the player has touched (`Player.ts:229-253`), afk zones, chat modes, lastLoginTime.
- Which inventories: `engine/content/scripts/player/configs/player.inv:1-10` defines `[inv] scope=perm size=28 protect=no` and `[worn] scope=perm size=14`; `engine/content/scripts/interface_bank/configs/bank.inv:1-4` defines `[bank] scope=perm size=^bank_total_slots stackall=yes` with `^bank_total_slots = 240` (`bank.constant:1`). Ids: `pack/inv.pack:94-96` -> `93=inv`, `94=worn`, `95=bank`. Coins: `pack/obj.pack:996` -> `995=coins`.
- When saves happen: logout -> `World.removePlayer` -> `flushPlayer` -> `logoutRequests.set(username, {save})` (`World.ts:1602-1628, 2366-2372`), retried every 15 s until the login thread acks (`World.ts:795-802`); autosave every `PLAYER_SAVERATE = 1500` ticks (`World.ts:124, 425-428, 1236-1243`). The single-world login thread writes the file synchronously (`LoginThread.ts:121, 142`). **The `.sav` file is the only persistence for bank contents** — nothing writes inventories to SQLite in either mode (`LoginServer.ts` only writes account/session/hiscore rows).
- Engine ignores `account_id` for persistence: files are keyed by username only. Renaming a character == renaming the file (inferred).

### F3. Bank mechanics and the minimal seam for a shared bank (handoff 5, 10.1)

- `Inventory` (`engine/server/src/engine/Inventory.ts`): `STACK_LIMIT = 0x7fffffff` (`:14`); `fromType` builds from `InvType` (size, `stackall` -> `ALWAYS_STACK`, shop stock) (`:20-44`); `add(id,count,beginSlot)` stacks when `objType.stackable || ALWAYS_STACK`, clamps at `STACK_LIMIT` and returns how many were added (`:107-150`); `remove` (`:152-215`); `set/get/delete`, dirty-slot tracking for `inv_transmit` (`:216-245`).
- `Player.getInventory(inv)` (`Player.ts:1471-1489`): `scope=shared` -> `World.getInventory(inv)` (one global container, `World.ts:1249-1260`); otherwise lazily creates a per-player container in `player.invs`. `invAdd/invDel/invSet` are thin wrappers (`Player.ts:1548-1582`).
- Script ops (`engine/script/handlers/InvOps.ts`): `INV_ADD :57-84` (overflow drops to floor), `INV_DEL :129-142`, `INV_MOVEITEM :496-531`, `_CERT :532`, `_UNCERT :567`, `INV_MOVETOSLOT :353`, `BOTH_MOVEINV :373` (trade/duel: moves one player's inv into another player's inv), `INV_TRANSMIT :641` / `INV_STOPTRANSMIT :662`. All run against `state.activePlayer`; protected invs require the `ProtectedActivePlayer` pointer unless `scope=shared` (`:64, :136, :504-510`).
- Bank RuneScript (`engine/content/scripts/interface_bank/scripts/bank.rs2`): `[label,openbank] :18-23` (`inv_transmit(inv, bank_side:inv)`, `inv_transmit(bank, bank_main:inv)`, `if_openmain_side`), `[label,closebank] :25-28` queues `reorganize_bank`, withdraw `:37-85` -> `inv_moveitem_uncert(bank, $inv, ...)`/`_cert`, deposit `:87-103` -> `inv_moveitem_uncert($inv, bank, ...)`, `bank_check_allowed :109`, insert mode `:133-142`. Opened from `bank_booth.rs2:1-7`, `banker.rs2`, and dev `[debugproc,bank]` (`scripts/_test/scripts/cheats/cheat_bank.rs2:1-4`).
- Options for a per-Firebase-user shared bank:
  - **(a) Engine-side owner-keyed bank.** Add an "owner key" to the player at login (e.g. new field in the `player_login` message from our own login shim, or derive from a `characters` lookup), and in `Player.getInventory` route `bank` (95) to a `World.ownerInvs: Map<ownerKey, Inventory>` shared by all online characters of that owner; persist it in its own file/DB row and exclude it from `.sav` (`Player.save :231-235` skip type 95; `PlayerLoading.load :129-136` skip). Files: `Player.ts`, `PlayerLoading.ts`, `World.ts` (load/save/evict owner bank), `LoginThread.ts`/`LoginServer.ts` (carry owner key), plus the transmit path (`inv_transmit` registers listeners per player, `Player.ts:1491+`; a second character with the bank open would not see the first's changes without cross-player listener refresh). Concurrency: all mutations are single-threaded on the world tick, so two online characters cannot corrupt the container; the risks are (i) stale UI on the other character until its next `inv_transmit` diff, (ii) migration of existing `.sav` bank slots into the owner store, (iii) engine is a pinned clone we "never edit" — this needs an overlay/patch strategy like `client/PATCHES.md`.
  - **(b) Front-server sync of per-character banks.** Keep engine banks per character; a front-server process reads/writes `.sav` files (format is small and documented above) to replicate bank 95 between characters of one uid. Files: new `server/src/sav/` codec, Firestore/SQLite ledger. Risks: the engine only reads `.sav` at login and overwrites it at autosave/logout, so a sync must run only while **all** characters of that uid are offline, and two online characters would have divergent banks until both log out; last-writer-wins clobbering is guaranteed otherwise. Not viable for "any character can access the same bank" while multiple are online.
  - **(c) Content-level.** Redefine `[bank]` as `scope=shared` — that makes one world-global bank for everyone (`Player.ts:1478-1480`), unusable. A content-only approach cannot key by owner because RuneScript has no notion of an account; it needs (a)'s engine hook anyway.
  - Recommendation: (a) with the smallest possible patch, described in Recommendation below.

### F4. Currency (handoff 19 "currency representation")

- `[coins]` obj (`engine/content/scripts/_unpack/225/all.obj:330-342`): `name=Coins`, `stackable=yes`, no `cost=` line -> `ObjType.cost` default 1 (`ObjType.ts:147`, loaded at `:206`). Id 995 (`pack/obj.pack:996`). Coins are just a stack in inv 93 or bank 95; a stack is capped at `Inventory.STACK_LIMIT` (`Inventory.ts:14,143`) and `INV_ADD` drops the overflow on the floor (`InvOps.ts:74-82`). There is no wallet/account balance anywhere else.

### F5. Item metadata and pricing (handoff 13, 15.2, 19)

- `ObjType` fields (`engine/server/src/cache/config/ObjType.ts`): `name :135`, `stackable :146`, `cost :147`, `members :148`, `certlink/certtemplate :165-166`, `weight :177`, `category :178`, `dummyitem :179`, `tradeable :180` (default true). Script accessors `OC_COST`, `OC_TRADEABLE`, `OC_STACKABLE`, `OC_MEMBERS` (`ObjConfigOps.ts:35-87`).
- Alchemy (`engine/content/scripts/skill_magic/scripts/spells/alchemy.rs2`): high `def_int $profit = max(scale(6, 10, oc_cost($item)), 1)` (`:25`), low `scale(4, 10, ...)` (`:61`), then `inv_del(inv, $item, 1); inv_add(inv, coins, $profit)`. So High Alchemy value = `max(floor(cost*0.6), 1)`, computable at build time from `cost`.
- Sources for a build-time item table: `*.obj` under `engine/content/scripts/**/configs` and `_unpack/225/all.obj` (names, cost, stackable, tradeable, members, certlink) + `pack/obj.pack` for ids. SPW spec already enumerates this (`docs/superpowers/specs/2026-09-05-spw-wiki-corpus-design.md:73`) and plans `wiki/gen/items.ts` (`:106,121`). SP3 references `scripts/gen/xp.ts` (`sp3 spec:57`) but `scripts/gen` does not exist in the repo yet (verified `ls scripts/gen` empty).

### F6. Hiscores and account-level wealth (handoff 15, 19 "High scores")

- `updateHiscores` (`LoginServer.ts:18-108`) writes `hiscore_large` type 0 (total xp) and `hiscore` per stat >= 15; called only from the login server's `player_logout` handler (`:457`). No other writer exists (grep `hiscore` over `engine/server/src` returns only these). Roadmap `:68-70` and SP3 `:28-33` are correct.
- SP3 plan (`sp3 spec:38-52, 62-75`): front-server SQLite `server/data/tracker.db` with `players(game_name UNIQUE, uid)`, `snapshots`, `latest`; ingest `POST /api/tracker/snapshot` authenticated by Firebase ID token, mapped to game name via `gameAccounts/{uid}` (`:67`). It is character-centric (`players.game_name`) with `uid` as a column — account-level grouping is a `GROUP BY uid` away.
- Where bank contents live: authoritative bank is in engine memory for an online character and in `.sav` for offline ones (F2). The client only sees bank 95 while the bank interface is open (`inv_transmit(bank, bank_main:inv)`, `bank.rs2:21`), and our hooks diff only component 3214 = inventory (`client/src/hooks/types.ts:62-63`), so **client snapshots cannot supply bank contents today**.
- Export paths that exist: none over HTTP. Management server exposes only `/prometheus`, `/setup`, `/setup/config` (`web.ts:319-347`). `wealth_event` (`PlayerOps.ts:1256-1267`) -> `Player.addWealthEvent` -> logger thread -> `session_wealth` (`LoggerServer.ts:55`) only when `logger.enabled` (`LoggerThread.ts:32-53`), and it records per-event deltas, not balances.
- Therefore account-level coin/wealth rankings need either (i) the engine to publish bank state (with option F3(a), the owner-keyed bank store is exactly the table to rank from), or (ii) a front-server `.sav` reader for offline characters plus a live query for online ones. With F3(a) the front server owns/reads the owner bank store directly and rankings are a single query; wealth = sum(count x price(item)) with price = market price else `max(floor(cost*0.6),1)`.

### F7. Engine-side mutation from outside (handoff 8, 10.1 settlement)

- Game-socket cheats (`network/game/client/handler/ClientCheatHandler.ts`): dev block `staffModLevel >= 4 && !production` runs `[debugproc,...]` scripts (`:57-62`; 247 debugprocs in content, e.g. `clearbank`, `maxme`, `addxp`); admin block `staffModLevel >= 3` (`:189`) has `setvar`, `give` (`:340-354` -> `player.invAdd(InvType.INV, obj, count)`), `giveother` (only in production, `:355`), `setstat`, `advancestat`; mod block `>= 2` (`:550`) `tele`, `ban`, `mute`, `kick`.
- Friend-server relay: a world sends `RELAY_QUEUESCRIPT {nodeId, scriptName, username}` to the friend server (`FriendServer.ts:385-396`), which relays to the target world (`World.ts:2064-2075`) where `player.enqueueScript([queue,<name>])` runs on that online player. Connection auth is only a matching `profile` string (`FriendServer.ts:96-102`); disabled in our config and only reaches online players.
- No engine HTTP mutation API, no offline mutation path, no script that can target an arbitrary username other than `giveother`/`teleother`-style cheats (online only).
- Consequence for Contracts settlement: server-authoritative transfers require one of: (1) F3(a) owner-keyed bank store that the front server can lock and mutate directly (offline-safe by construction, and the engine loads it on demand), (2) a tiny engine management route added by patch (`management.post('/player/:name/inv')`) that enqueues a script on an online player and edits `.sav` for an offline one (fragile: races with autosave), or (3) a content `[queue,contract_settle]` script triggered via RELAY_QUEUESCRIPT (online only, needs friend server enabled). Trade precedent for atomic two-party moves is `both_moveinv` (`InvOps.ts:373`, used by `trade.rs2:265-266`).

### F8. Deletion (handoff 6.2)

- Engine: no code path deletes a `.sav` or an `account` row (grep `unlink|rmSync` over `engine/server/src` hits only cache/datastructure code). A character is deleted by removing `data/players/main/<name>.sav` while the player is offline (otherwise autosave/logout recreates it — `LoginThread.ts:121,142`).
- Ours: routes are `/`, `/api/health`, `/api/gate`, `/api/bridge`, `/api/pair`, `/connect` (`server/src/router.ts:25-30`); nothing deletes `gameAccounts`/`gameNames`. Firestore rules deny all client writes to those collections (`firestore.rules:29-30`) and `users/{uid}` delete (`:18`).
- Agent side: agent tokens are `agentTokens/{id} = {uid, label, secretHash, mode}` (`server/src/pair/store.ts:112-121`, SP4 spec `:44`); the MCP gateway (`/mcp`) is bearer-agentToken. So "what prevents agent deletion today" is simply that no deletion API exists; the enforcement to design is: the delete route accepts only a Firebase ID token (never an agent token), re-verifies `gameNames/{name}.uid == uid`, requires a fresh sign-in/second factor, and the engine kicks the character first (no `.sav` rewrite after removal).

## Implications for the handoff

- **2.2 / 6.1 characters per uid**: replace `gameAccounts/{uid}` (one name + one secret) with `characters/{name} = {uid, createdAt, slot}` and `users/{uid}.characterNames[]`; keep `gameNames/{name}` as the uniqueness index. Creation is purely front-server (allocate name, no engine call); the `.sav` appears on first logout. The per-character `secret` is pointless for the engine but is the shell/agent capability token — keep one per character. Character limit enforcement (guest 1, free 3) lives in the same transaction.
- **6.3 "Log in as <character>"**: unchanged engine handshake — username + any password. Real protection against name-only login needs the relay (`server/src/proxy/ws.ts`) to bind the socket to a uid-owned character (inspect the login packet, `World.ts:2198-2200` layout) — recommend doing that in Phase C.
- **5 / 10.1 shared bank + settlement**: only F3(a) satisfies "any character accesses the same bank while others are online" and "server-authoritative settlement, offline included". It is an engine patch, so the "never edit engine" rule needs an explicit overlay/patch mechanism for `engine/server` (mirroring `client/PATCHES.md`). Design the owner bank store so the front server is the owner (SQLite table `bank_items(uid, slot, obj, count)` or a JSON file per uid) and the engine loads it at login / writes it on change or autosave with an optimistic version; Contracts settlement then locks rows in the front server and pushes a delta to the engine only if the owner has a character online.
- **15 hiscores**: account-level coin and wealth rankings should read the owner bank store, not client snapshots. Character inventory/worn (per-character, in `.sav`) can be included via a `.sav` reader or excluded by definition ("bank wealth"). Double-counting is avoided by ranking uid, not character.
- **13 market data / 15.2 alch fallback**: build-time item table from `*.obj` is sufficient; HA value formula verified.
- **17 security**: `node.production=false` grants every player staffmodlevel 4 (`LoginThread.ts:65-67`) — must be `true` (or the engine patched to take staff level from our login shim) before any economy feature ships.

## Open questions

1. Engine patch policy: `engine/server` is a git-ignored pinned clone. Do we adopt a patch file + apply script (like `client/PATCHES.md`) or fork Engine-TS? F3(a)/F7 both need it.
2. Bank interface UX with two characters banking at once: acceptable to show stale slots until reopen, or do we add cross-player `inv_transmit` refresh in the patch?
3. Should character inventory (93) and worn (94) count toward wealth rankings? If yes, the front server needs a `.sav` reader (format in F2) or the engine must publish per-character totals.
4. Guest characters: are they `.sav` files that expire? Engine never deletes; a reaper is our job.
5. Owner bank capacity: keep 240 (`^bank_total_slots`) per uid, or larger since three characters share it?
6. Does Contracts settle into the bank only (simplest, offline-safe) or also into a live character's inventory?

## Recommendation

- Adopt F3(a): an engine overlay patch that (1) accepts an `ownerKey` in `player_login` (our login shim derives it from `characters/{name}.uid`), (2) routes inventory 95 to a `World.ownerBanks` map persisted by a small `OwnerBankStore` (file or SQLite in `engine/server/data/banks/<ownerKey>.json`, versioned), (3) skips type 95 in `Player.save`/`PlayerLoading.load` with a one-time migration of existing `.sav` banks, (4) exposes two management routes on port 8897: `GET /owner/:key/bank` and `POST /owner/:key/bank/apply` (delta with expected version, applied on the world tick; 409 on mismatch). The front server (Contracts, hiscores) uses those routes; everything else (character CRUD, ownership, limits, deletion) stays in `server/` + Firestore.
- Before that: set `node.production=true` (or patch staff level to come from the shim), and bind relay sockets to owned characters.
- Deletion: front-server-only route, Firebase ID token only, kick-then-remove, never reachable via `/mcp`.
