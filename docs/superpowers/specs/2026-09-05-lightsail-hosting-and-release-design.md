# Lightsail hosting and release process — design

Date: 2026-09-05. Status: approved in chat, implementing.

## Goal

Move the public idlescape stack (274 engine + front server + Cloudflare tunnel connector)
off this PC onto a small AWS Lightsail box, and give this repo a repeatable, operator-run
release process that ships a committed revision to that box and brings it up.

## Constraints that shaped the design

- **Account.** AWS account 000000000000 is on the AWS *Free plan*: $100 credit, plan expires
  2027-03-05, no charges possible, account closes at expiry unless upgraded to the Paid plan
  (90-day grace, resources retained). Spend must stay under ~$16.80/month to outlast the plan.
- **Sizing.** Measured on this PC: the 274 engine sits at ~475 MB resident, the front server at
  ~65 MB, both at a few percent of one core. The cache pack step (run inside the engine image
  build) can spike past 2 GB. Steady state fits 2 GB; the build needs swap.
- **No Docker on this PC.** Images are built on the server. This also means the release must
  carry source, not images.
- **No git remote on this repo.** Releases ship from the local checkout over SSH; nothing is
  pulled from a hosted repository.
- **Existing deploy files.** `deploy/docker/` (compose + two Dockerfiles + world template) was
  authored for an Oracle ARM VM and never run. Nothing in it is architecture-specific; it is
  reused as-is except for the cloudflared service (below).
- **Tunnel.** The `idlescape` Cloudflare tunnel (id `00000000-…`) currently serves
  `osrs.scotho.com` from this PC's `idlescape-tunnel` scheduled task, pointing at the 225 PoC
  on port 8888. Its credentials JSON and `cert.pem` are in `%USERPROFILE%\.cloudflared`.
- **Firebase.** Project `idlescape-osrs` exists. The front server needs a service-account key
  when `FIREBASE_EMULATORS=false`; one was created with gcloud into `server/secrets/` (git-ignored).

## Decisions

| Decision | Choice | Why |
|---|---|---|
| Machine | Lightsail `small_3_0` bundle, Ubuntu 24.04, ca-central-1a. 2 vCPU / 2 GB / 60 GB SSD / 3 TB transfer, $12/mo | Only option that outlasts the plan with headroom; flat price includes disk, IP, egress |
| Build memory | 4 GB swapfile created by user-data | Pack step exceeds 2 GB; swap is free on the 60 GB disk |
| SSH | Dedicated RSA-4096 key `~/.ssh/idlescape-lightsail`, imported to Lightsail as `idlescape-lightsail` | Local `id_rsa` is ECDSA, which Lightsail will not import |
| Inbound firewall | SSH (22) only; drop the default port 80 rule | Only cloudflared talks to the internet, outbound |
| Tunnel connector | Locally-managed: mount `config.yml` + credentials JSON into the cloudflared container, ingress `osrs.scotho.com -> http://server:8787` | No dashboard trip; reuses credentials already on this PC. Replaces the token-based service in compose |
| Release transport | `git archive HEAD` streamed over SSH, extracted to `/opt/idlescape/src`, then `docker compose build && up -d` on the box | Only committed files ship, so every release is a known commit; no registry, no remote needed |
| Secrets transport | One-time `provision` step copies `server/.env`, `server/secrets/firebase-admin.json`, tunnel credentials, and a generated `deploy/docker/.env` | Secrets never ride in the archive (`.dockerignore` already excludes them from the image) |
| `deploy/docker/.env` | Generated by provision from `scripts/upstream.lock` (shas) and `web/.env.local` (VITE values) | Removes the hand-copy step the README called out as error-prone |
| Health check | Release script opens an SSH port-forward to `server:8787` and polls `/api/health` until the engine reports up | Verifies without touching the public hostname |
| Cutover | Explicit `cutover` step: verify health, then stop the PC's `idlescape-tunnel` task (elevated) | Two connectors with different ingress route unpredictably, so the old one must stop in the same window |

## Components

```
deploy/lightsail/
  provision.ps1     create instance (idempotent by name), wait for SSH, push secrets + generated env
  release.ps1       archive HEAD -> ssh -> compose build/up -> health check via port-forward
  cutover.ps1       (elevated) confirm remote health, stop idlescape-tunnel task on this PC
  user-data.sh      cloud-init: docker engine + compose plugin, 4 GB swap, /opt/idlescape dirs
  cloudflared.yml   tunnel config mounted into the container (ingress -> http://server:8787)
  README.md         operator runbook (supersedes deploy/docker/README.md's Oracle VM steps)
deploy/docker/docker-compose.yml   cloudflared service switched to config+credentials mounts
```

Server layout: `/opt/idlescape/src` (extracted archive, replaced each release),
`/opt/idlescape/secrets/` (server env, firebase key, tunnel credentials, compose env).
The compose project is run from `/opt/idlescape/src/deploy/docker` with `--env-file`
pointing at the secrets directory, so `git archive` never has to contain env files.

## Data flow of a release

1. `release.ps1` refuses to run with uncommitted changes to tracked files unless `-Force`.
2. `git archive --format=tar HEAD | ssh box 'rm -rf src.new && mkdir src.new && tar -x -C src.new'`, then swap `src` <- `src.new`.
3. Symlink `server/.env` and `server/secrets/firebase-admin.json` from the secrets dir into the fresh tree (compose reads them by relative path).
4. `docker compose --env-file /opt/idlescape/secrets/compose.env build` then `up -d --remove-orphans`.
5. Port-forward `localhost:18787 -> server container 8787` (via `docker compose exec`-free path: publish nothing; use `ssh -L` to the box and `docker run --network` curl inside the compose network). Poll `/api/health` until `engine` is `up` or timeout.
6. Print the released commit sha and health JSON.

## Error handling

- Provision is idempotent on instance name; re-running only re-pushes secrets.
- Release keeps the previous `src` until the new archive extracted cleanly.
- Health timeout leaves containers running and prints `docker compose logs --tail` for both services so the operator can decide.
- Cutover refuses if remote health is not up.

## Testing

- Scripts are exercised for real against the box in this session (no unit tests; they are thin
  orchestration over ssh/aws/docker).
- Acceptance: `/api/health` reports the engine up through the port-forward; after cutover,
  `https://osrs.scotho.com/api/health` returns the same and the title screen loads.
